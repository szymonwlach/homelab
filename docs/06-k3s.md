# 06 - Kubernetes with k3s

## Goal

k3s is a lightweight distribution of Kubernetes (k8s), stripped down enough to
run on a single old laptop. The point was to learn how modern container
orchestration actually works, beyond running containers with Compose.

## Install

```bash
curl -sfL https://get.k3s.io | sh -
kubectl get nodes
```

```
NAME      STATUS   ROLES           AGE   VERSION
homelab   Ready    control-plane   31s   v1.36.3+k3s1
```

One command, one node, `Ready`. A single-node cluster is still a cluster.

`kubectl` initially needed `sudo`, because the cluster config at
`/etc/rancher/k3s/k3s.yaml` is owned by root. Same class of problem as needing
`sudo docker` before joining the `docker` group. Fixed by copying it into the
user's home directory:

```bash
mkdir -p ~/.kube
sudo cp /etc/rancher/k3s/k3s.yaml ~/.kube/config
sudo chown $USER:$USER ~/.kube/config
chmod 600 ~/.kube/config
echo 'export KUBECONFIG=~/.kube/config' >> ~/.bashrc
```

`chmod 600` matters: that file contains cluster credentials, effectively the
keys to everything.

## What k3s brings up on its own

```bash
kubectl get pods -A
```

Nothing was deployed yet, but the `kube-system` namespace already had:

| Component                | Role                                                | Compose equivalent     |
| ------------------------ | --------------------------------------------------- | ---------------------- |
| `coredns`                | in-cluster DNS, services resolve each other by name | Compose's built-in DNS |
| `local-path-provisioner` | persistent storage for pods                         | named volumes          |
| `metrics-server`         | basic CPU/memory usage for autoscaling              | (none)                 |
| `traefik`                | ingress controller, entry point from outside        | the `ports:` section   |

Namespaces are logical partitions inside a cluster. System components live in
`kube-system`, so a plain `kubectl get pods` shows nothing until you deploy
something of your own into `default`.

## The moment it clicked

Deployed nginx with 3 replicas, then deleted one pod by hand:

```bash
kubectl delete pod nginx-test-c8697b5cc-z4vwm
kubectl get pods
```

```
nginx-test-c8697b5cc-fwsst   1/1   Running   0   6s
```

A new pod, different name, six seconds old. Nothing restarted it. Nothing was
told to recreate it.

The Deployment declares "there should be 3 of these". Kubernetes constantly
compares that declaration against reality, and when the two diverge, it closes
the gap on its own. That loop is the whole idea.

Note `RESTARTS: 0`. It wasn't a restart. The old pod was gone for good and a
new one took its place. Pods are disposable by design.

## Deployment → ReplicaSet → Pod

```bash
kubectl get all
```

Two objects were declared, five appeared:

```
deployment.apps/nginx-test
  └── replicaset.apps/nginx-test-5c8494dc44
        └── pod/...grclc, pod/...qrvwd, pod/...zqgkv
service/nginx-test
```

Deployment manages a ReplicaSet, the ReplicaSet manages Pods. You only write
the top of that chain. The ReplicaSet layer exists for rolling updates: on a
new image, the Deployment creates a _second_ ReplicaSet and shifts pods across
one at a time, so the app never goes fully down.

## Services and labels

Each pod gets its own IP:

```
nginx-test-...-5nvvd   10.42.0.12
nginx-test-...-frrr5   10.42.0.11
nginx-test-...-fwsst   10.42.0.10
```

Those IPs change every time a pod is replaced, so nothing can point at them
directly. That's what a Service is for: one stable address in front of a
changing set of pods, distributing traffic between whichever ones are alive.

The connection between them isn't direct. It runs through labels:

```yaml
# Deployment: which pods do I manage?
selector:
  matchLabels:
    app: nginx-test

# Pod template: what sticker do I wear?
labels:
  app: nginx-test

# Service: where do I send traffic?
selector:
  app: nginx-test
```

Deployment and Service never reference each other. Both independently query for
pods carrying the same label. Elegant, but it means a mismatched label sends
traffic nowhere, with no error message that points at the cause. Same failure
mode as `alert-rules.yml` vs `alert_rules.yml` and `random-metric` vs
`random-metrics` earlier in this repo: names that look identical at a glance,
silent failure when they aren't.

## Why replicas matter, even when nothing is visible

With the page open in a browser, deleting a pod changed nothing. No error, no
flicker, no downtime. That non-event is the point.

- **One replica**: a crashing pod means the site is down until a new one starts.
- **Three replicas**: the Service stops routing to the sick one, the other two
  carry on, and the user never notices.

It also unlocks horizontal scale (more replicas, more throughput), spreading
across physical machines in a multi-node cluster, and zero-downtime rolling
updates.

Good infrastructure is invisible. Nobody notices it working; they only notice
when it stops.

## Declarative, from the repo

The first attempts used imperative commands (`kubectl create deployment`,
`kubectl scale`, `kubectl expose`). Fine for learning, wrong for real work:
nothing is recorded, nothing is reproducible, and nobody can tell what's
actually deployed.

Everything moved into [`k8s/nginx.yaml`](../k8s/nginx.yaml), two objects in one
file separated by `---`, applied with:

```bash
kubectl apply -f k8s/nginx.yaml
```

Changing replicas from 3 to 5 meant editing the file and running the exact same
command. Kubernetes added two pods and left the existing three untouched.

That's idempotence: run it ten times and the result is the same, because you're
declaring a target state rather than issuing instructions. It's simpler than
Compose in this respect, where the right command depended on what changed
(`restart` for file contents, `up -d` for structural changes).

Images are pinned (`nginx:1.27`) rather than `:latest`, paying down a shortcut
noted earlier in this repo.

## Compose vs Kubernetes

Compose **creates** containers, and with `restart: unless-stopped` it will
bring one back when its process dies.

Kubernetes **maintains a declared state**. It doesn't care _why_ reality
diverged, whether the process crashed, a pod was deleted by hand, or an entire
node disappeared. It compares "how many should exist" against "how many do",
and closes the gap. That distinction is why deleting a pod produced a _new_
pod rather than a restarted one.

## What I learned

- **Declaring a state beats issuing commands.** The system holds the state for
  you instead of you re-checking it.
- **Pods are disposable, and that's deliberate.** Never point anything at a
  specific pod; point it at a Service.
- **Labels are the glue.** Nothing references anything else directly, which is
  flexible and also means a typo fails silently.
- **You declare the top of a hierarchy and get the rest for free.** Deployment
  → ReplicaSet → Pod.
- **Availability is something you configure, not something you hope for.**
  Replicas are the difference between "the app runs" and "the app runs while
  things break."
- **The cluster survived a full power-off.** Shut the server down overnight,
  powered it back on, and every pod came back without intervention.
